## Overview

This project was developed as part of Kookmin University's AI for Business track during the Global PBL Program in Irvine. In this coursework case study, Renaissance Technologies (RenTech) was treated as a hypothetical client.

The project focused on designing a hybrid cloud migration strategy for a large quantitative hedge fund managing high-volume historical market data and compute-intensive research workloads.

The goal was not to move everything to AWS, but to determine which workloads were appropriate for cloud migration and which should remain on-premise due to latency, security, and operational constraints.

## The problem

RenTech's research environment relies heavily on large-scale backtesting and model experimentation. These workloads require massive compute resources during quarter-end research cycles but remain underutilized for much of the year.

At the same time, certain systems, especially live trading infrastructure, cannot tolerate additional latency or external exposure. For a quantitative trading firm, execution speed and protection of proprietary strategies are critical.

This created a key architectural question:

Which workloads should remain on-premise, and which could benefit from cloud elasticity?

## My role

I worked as the Solutions Architect on a four-person AWS sales simulation team.

My responsibilities included:

- hybrid architecture design
- workload separation strategy
- infrastructure cost modeling
- migration boundary decisions
- technical presentation to hypothetical stakeholders

The proposal went through multiple revisions as we narrowed the migration scope and reduced unnecessary complexity.

## Key architectural decisions

### 1. Hybrid workload separation

The final proposal separated workloads based on latency sensitivity and operational risk.

**On-premise systems included:**

- live trading execution
- model serving
- proprietary alpha infrastructure
- low-latency networking systems

**AWS-hosted systems included:**

- quarterly backtesting workloads
- large-scale model training
- historical market data storage

The reasoning was that backtesting workloads are highly compute-intensive but time-bounded, making them well suited for burst-based cloud scaling.

### 2. Burst-based compute scaling

Instead of maintaining enough GPU infrastructure to handle quarter-end peaks year-round, the proposal used AWS elastic scaling for temporary compute demand.

GPU infrastructure scaled dynamically from:

- 20 baseline GPUs
- up to 200 GPUs during quarter-end backtesting periods

CPU infrastructure followed a similar model using scalable EC2 instances.

This significantly reduced idle infrastructure costs while still preserving peak compute capacity during research cycles.

### 3. Tiered storage architecture

The proposal also redesigned historical market data storage using a three-tier S3 strategy:

- S3 Standard for recent data
- S3 Infrequent Access for mid-term storage
- Glacier Deep Archive for long-term retention and compliance storage

This reduced long-term storage costs while keeping frequently accessed datasets readily available.

### 4. Simplifying the migration scope

One of the biggest changes between early and final proposal versions was reducing unnecessary migration complexity.

Earlier versions attempted to migrate more aggressively using services such as AWS FinSpace and Snowmobile. However, later revisions prioritized:

- fewer vendor dependencies
- tighter security boundaries
- simpler operational architecture
- lower migration risk

The final proposal favored a more conservative hybrid approach rather than a full infrastructure rewrite.

## Final outcome

The final architecture reduced estimated annual infrastructure costs from approximately **$36M/year to $25.5M/year**, while preserving:

- low-latency live trading systems
- proprietary infrastructure security
- operational control over sensitive workloads

The proposal ultimately balanced:

- cloud scalability
- cost efficiency
- operational risk
- performance requirements

## What I learned

The biggest lesson from this project was that good architecture decisions are often about defining boundaries clearly.

At the beginning of the project, our team focused too much on how much could move to the cloud. Over time, the discussion shifted toward which workloads actually should move.

That changed how I think about technical strategy more broadly. Good system design is not about maximizing complexity or migration scope. It is about identifying where different systems operate most effectively and making tradeoffs intentionally.
